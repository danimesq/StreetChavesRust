# Fighter data deep dive

## Scope and evidence

Comparison of pinned source/data representations, not a Rust schema and not proof either port is canonical.

- Pascal/SDL2: [OpenStreetChaves](https://github.com/danimesq/OpenStreetChaves/tree/e1b025c35ecbc2b14d8635564aafd23c2107d3d1), `e1b025c35ecbc2b14d8635564aafd23c2107d3d1`.
- C17/SDL3: [open-street-chaves](https://github.com/danimesq/open-street-chaves/tree/e76ad2188af6842ff6618ecdb8f425bba61c9183), `e76ad2188af6842ff6618ecdb8f425bba61c9183`.

**Source-observed** means visible in checked-in code/data. **Decompiler/spec evidence** means analysis of the original executable, not original source. **Inference** is provisional. **Open** means not established. The SMS ROM hack is not evidence for PC fighter mechanics.

## Findings

1. Pascal stores fighter parameters, command recognition, sprite anchors, hurtboxes, hitboxes and executable move scripts in `CNN.ini` + `CNN.rot`, with shared behavior in `Comum.rot`.
2. `.rot` is a custom Pascal-like language interpreted at runtime. Scripts mutate gameplay state and call engine helpers; they are not animation metadata.
3. C stores reverse-engineered behavior in `docs/spec/`; `tools/gen_tables.py` parses those specs into generated C tables. Hand-written selector/move code still supplies behavior outside the rows.
4. The representations do not map one-to-one. Similar names do not prove identical semantics.
5. Pascal has C01..C15 for the original roster plus C16 Chapolin, a separately documented generated extension. C models the original 15 fighters.
6. Preserve ordered rules, distinguish sprite-frame indexes from action timers, and represent missing values explicitly. Do not invent defaults or interpolate collision boxes.

### C16 Chapolin is an extension

Pascal's `C16.ini` and `C16.rot` define Chapolin. The INI header says its art and `CentroX`, `Corpo`, `Ataque` data are generated by `source/tools/GeraChapolin`. It describes C16 as a harder CPU opponent (walk speed 9.0, stronger attacks, more frequent special use). The C reference does not include C16.

C's generated `osc_frame_offset[16][64]` has an index-zero row; it is not evidence of 16 fighters. Keep Chapolin optional until its game-mode availability and asset provenance are reviewed. See [Chapolin: 2026 bonus preservation plan](chapolin-bonus-2026.md) for the recovery plan.

## Pascal data package

Primary files: `source/game/ChavesDados.pas` (INI loading), `ChavesGolpes.pas` (fighter frame data and box loading/application), `ChavesRoteiro.pas` (script interpreter), `ChavesTipos.pas` (IDs and fighter record), `Estado7_Golpes.inc` and `Estado7_Luta.inc` (fight consumers), plus `Dados/Lutadores/Comum.rot`, `C01..C16.ini` and `C01..C16.rot`.

All 16 inspected INIs have seven sections: `[Geral]`, `[Golpes]`, `[Sequencias]`, `[Botoes]`, `[CentroX]`, `[Corpo]`, `[Ataque]`.

All 16 character ROT files have `[Acao]`, `[Quadro]`, `[IA]`. `[Acerto]` is optional and absent in C08, C13 and C14. `Comum.rot` has `[Acao]`, `[AcaoFim]`, `[Quadro]`, `[IA]`; no shared `[Acerto]` exists in this pinned file.

### INI sections

| Section | Entry shape / purpose | Important distinction |
|---|---|---|
| `Geral` | Sprite height, walk speed, campaign boss/exclusions, stage and CPU music | Defaults come from individual read sites |
| `Golpes` | Ordered display name + notation; `*` marks final move | Presentation list, not command parser |
| `Sequencias` | Ordered condition + `from>to` transition | Relative directions, hold counters; order matters |
| `Botoes` | Ordered button + conditions -> command | All matching rules execute in order |
| `CentroX` | Sprite frame -> horizontal anchor offset | Sprite frame, not action timer |
| `Corpo` | Sprite frame -> `x1,y1,x2,y2` hurtbox | Relative to feet; mirrored by facing |
| `Ataque` | `action.timer[.f1|.f2]` -> box, active, strength, damage, guard damage | Action timer, not sprite frame |

INI conventions in `ChavesDados.pas`: semicolon comments; decimal parser accepts dot and replaces comma with dot; comma-separated lists are trimmed; missing/invalid decimals use caller fallback; paths resolve relative to game root. `ArquivoNN` replaces the first contiguous run of `#` with a zero-padded number. Duplicate keys, malformed lists, case and whitespace behavior still need tests.

#### `[Geral]`

Observed keys include `AlturaSprite`, `Velocidade`, `Chefe`, `NaoEnfrenta`, `Cenario`, `CenarioAlternativo`, `CenarioRaro`, `MusicaCPU`. Do not assume absent-key defaults from a single fighter file; record each loader read site.

#### `[Golpes]`

Ordered numeric entries contain display name and notation, e.g. `1=Power Wave,BDP`. The leading `*` marks the final/super move. This section does not itself implement command recognition.

#### `[Sequencias]`

Conditions include `Baixo`, `Frente`, `Tras`, `Cima`, negated directions, `TempoBaixo>=N`, `TempoTras>=N`, `NoChao`. Front/back are relative to facing. Comments say rules are evaluated in order every fight frame and sequence state resets after nine frames without advancement. Hold counters cap at 18 and decay gradually. A transition only applies when the current state matches `from`; each character has its own transition graph.

#### `[Botoes]`

Conditions include `Passo=N`, `NoAr`, `CargaSoco>=N`, `CargaChute>=N`. The four attack buttons map to commands such as `Esp1Fraco`, `Esp4Forte`, `EspFinal`, `EspExtra1`, `EspExtra2`. The file comments say all matching rules execute in order. Do not reduce this to a first-match map.

#### `[CentroX]`, `[Corpo]`, `[Ataque]`

`CentroX` is keyed by sprite frame. `Corpo` is keyed by sprite frame and defines the hurtbox. `Ataque` is keyed by action and action timer, optionally restricted by `.f1` or `.f2`. Values are `x1,y1,x2,y2,active,strength,damage,guard_damage`. Source comments say attack rows are applied in file order and strength may change while applying them.

C01 has frame anchors through 49; C16 through 50. Data comments say player two adds 50 to the frame index. These are examples, not universal maxima. Missing rows must follow actual consumer behavior; do not interpolate.

## Pascal `.rot` interpreter

`ChavesRoteiro.pas` parses a restricted Pascal-like language into an internal node representation. Documented syntax includes `if/then/else`, `begin/end`, `for/to/downto`, `repeat/until`, `while`, `case`, assignments, calls, sets (`in [...]`) and typed locals: Byte, ShortInt, SmallInt, Word, Integer, Int64, Double and Boolean.

Scripts access `P.` (acting fighter), `O.` (opponent), `Jog`, `Codigo`, `Desloc`, game globals/constants and helpers including `Random`, `Round`, `Trunc`, `Abs`, `Cos`, `Sin`, `ShortInt`, `ExisteEfeito`, `CriaEfeito`, `Empurra`, `AcaoJogador`, `AplicarCaixas`.

Numeric semantics matter: integer operations can remain integer; division and expressions involving Double produce real values; narrow integer assignment converts/truncates. Random calls pass through a record/replay facility. Rust casts, evaluation order and RNG must not be assumed equivalent.

Documented composition:

- Action: shared `Comum.rot [Acao]`, character `CNN.rot [Acao]`, shared `[AcaoFim]`.
- Frame update: shared `[Quadro]`, character `[Quadro]`, then `AplicarCaixas`.
- CPU: shared `[IA]`, then character `[IA]`.
- Hit reaction: optional character `[Acerto]` after standard hit/damage/reaction/pushback.

Frame scripts can mutate state/action, frame, position, velocity, invulnerability, attack flags, sound requests and effects. This is simulation logic, not passive animation. Examples: C08 gates an air special on jump state and prevents duplicate effect ownership; C13 has extra move commands and character-specific movement; C16 creates effect types 37/38 and custom sound/frame behavior.

## C17 specification and generated tables

The C project treats `docs/spec/` as its editable evidence/data layer. `tools/gen_tables.py` reads the text specs and emits `src/gen/tables_gen.c` and `tables_gen.h`; the generated header says not to edit it manually.

Relevant inputs:

- `04-moves.md`: move IDs, notation, command parser, CPU.
- `04a-move-tables.txt`: per-character direction transitions and button-to-move mapping.
- `05-fight-engine.md`: state machine, timing, move setup and combat.
- `05a-anim-tables.txt`: hurtboxes and hitboxes.
- `05b-move-setup.txt`: allowed source states, target state, duration, meter and sound.
- `05c-frame-offsets.txt`: per-character frame anchors.
- `05d-cpu-table.txt`: CPU decisions.
- `06f-selector-frames.txt`: frame-selection rows.
- `06g-selector-stores.txt`: guarded field writes.
- `06d-special-motion.txt`, `06e-selector-spawns.txt`, `06c-special-sounds.txt`: special movement, effect spawns and sounds.

Pinned generated dimensions:

|---|---:|---|

### C move IDs

The C spec describes common IDs 1..15 and character-specific IDs 16..26. Special pairs generally represent weak/strong variants: 16/17, 18/19, 20/21, 22/23; 24 is the super/final; 25/26 are extra Jaiminho moves in this spec. Per-character setup controls allowed source states, target state, duration, meter, sound and effect prerequisites. Some slot/list mappings are explicitly marked as inference.

### C frame selector order

In pinned `src/fight/selector.c`, `select_frame` calls:

1. `sel_frames`: apply matching frame rows; later rows may overwrite earlier choices.
2. `sel_stores`: apply guarded field writes and hand-coded exceptions.
3. `special_motion`: special movement.
4. `sel_run_turn`: Sr. Furtado run-turn exception.
5. `fx_spawns_for`: effect creation.
6. `fx_sounds_for`: sound queueing.
7. `sel_boxes`: hurtbox and attack-row selection.

The frame spec says that if no row fires, the current frame remains unchanged. Hand-coded throw/special behavior is not fully represented by generated rows.

## Representation comparison

| Concern | Pascal | C |
|---|---|---|
| Character parameters | INI `[Geral]` | Constants/tables/runtime |
| Move list | INI `[Golpes]` | Original strings/spec |
| Command transitions | `[Sequencias]` | `osc_seqs` |
| Button mapping | `[Botoes]` | `osc_golpe` |
| Sprite anchor | `[CentroX]` | `osc_frame_offset` |
| Hurtboxes | `[Corpo]` | `osc_hurt` |
| Attack boxes | `[Ataque]` | `osc_hit` |
| Action/frame logic | Interpreted `.rot` | Generated tables + hand-written C |
| CPU specials | `.rot [IA]` | `osc_cpu` + CPU code |
| Hit reactions | Optional `.rot [Acerto]` | Combat/selector exceptions |

This is conceptual, not semantic equivalence.

## Open questions and next research

- Extract every `[Geral]` key, read site and fallback.
- Test INI duplicate keys, malformed values, case/whitespace and list behavior.
- Document full sequence/button condition grammar and invalid-input behavior.
- Trace missing-frame defaults and overwrite order for all attack rows.
- Inventory every script-visible `P.`/`O.` field with type, width, signedness and meaning.
- Build interpreter conformance tests for conversion, short-circuiting, evaluation order, sets, loops and RNG replay.
- Build a 15-character move matrix: inputs, source states, state/action, duration, meter, frames, hitbox windows, damage, guard damage, effects, sounds and CPU use.
- Compare every Pascal/C fighter rule with original executable captures; record executable hash and data-folder identity.
- Determine C16 game-mode availability and generated-art provenance.

## Rust-facing implications (not a schema)

1. Keep the original 15-character roster distinct from optional extensions such as Chapolin.
2. Treat `.rot` as executable behavior until verified extraction proves otherwise.
3. Preserve ordered rule evaluation and multiple-match semantics.
4. Keep sprite frame, action timer, state ID and command-sequence state distinct.
5. Keep hurtbox lookup (character + sprite frame) separate from attack lookup (character + action/state + timer).
6. Model missing data/defaulting explicitly; no interpolation or guessed fallback.
7. Tag original-executable evidence, Pascal behavior and C behavior independently.
8. Do not copy scripts or original assets into this repository.
